# Автоматическая генерация признаков для ранжирования рекомендаций

Исследование на датасете [KION](https://github.com/irsafilo/KION_DATASET) (МТС): может ли автоматический поиск по пространству признаков заменить ручной feature engineering для LightGBM-ранкера без потери качества.

Всё исследование в одном ноутбуке: [solution.ipynb](solution.ipynb). Здесь краткое изложение.

## Постановка

- **Задача:** по истории до даты `T` выбрать 10 тайтлов, которые пользователь посмотрит в неделю `[T, T+7)`. Уже просмотренное не рекомендуется.
- **Данные:** случайные 100 тыс. пользователей с полной историей, 573 тыс. просмотров.
- **Разбиение по неделям:** `train` 02–08.08, `val` 09–15.08, `test` 16–22.08.2021. Признаки каждой недели считаются только по событиям до её начала.
- **Двухстадийная схема:** популярность + ItemKNN дают около 170 кандидатов на пользователя (покрывают 44% позитивов), LightGBM `lambdarank` их ранжирует.
- **Метрики:** NDCG@10, Recall@10, MAP@10, ROC-AUC. Доверительные интервалы считаются бутстрепом по пользователям, сравнение с ручным набором — парным бутстрепом.

## Подход

Признаки описываются грамматикой: `(связь, тип события, окно или затухание, агрегация, нормировка, свёртка)`. Например, `ua:genre / complete / h30 / cnt / lift / max` означает «насколько чаще среднего пользователь досматривает жанры кандидата, с затуханием 30 дней». Спецификация компилируется в SQL для DuckDB. Пространство содержит 7 389 допустимых признаков, ручной набор — 29 его точек.

Утечки исключены конструктивно: единственный источник событий для признаков — таблица с отсечкой по дате. Это проверяется тестом: признаки не меняются, если удалить из лога все будущие события.

Сравниваются:

| Подход | Что делает человек | Как выбираются признаки |
|---|---|---|
| Ручные | придумывает 29 признаков | никак |
| Сетка + фильтр (как DFS) | задаёт сетку из 1 004 признаков | одномерный AUC внутри пользователя, удаление дублей |
| Жадный, случайный пул | задаёт пространство | 12 шагов: 24 кандидата → дешёвая оценка → 4 лучших → полная модель → принять, если NDCG растёт |
| Жадный, пул от LLM | задаёт пространство | то же, но кандидатов предлагает LLM (Nemotron 3 Ultra через OpenRouter), видя историю поиска |

## Результаты

Основная тестовая неделя — 16–22.08. Для проверки устойчивости те же замороженные наборы признаков оценены на неделе 26.07–01.08 (разбиение сдвинуто на три недели назад; эти недели в поиске не участвовали).

Названия подходов в таблице:
- **жадный** — признаки добавляются по одному: на каждом шаге из кандидатов выбирается тот, что сильнее всего улучшает NDCG на валидации, а уже выбранные не удаляются;
- **случайный пул** — кандидаты на каждом шаге выбираются случайно из всех 7 389 признаков грамматики (затем остаются 24 лучших по AUC внутри пользователя);
- **пул от LLM** — кандидатов на каждом шаге предлагает языковая модель, видя историю поиска;
- **сетка + фильтр** — все признаки фиксированной сетки (окна 7, 30 дней и вся история) отбираются по отдельности, без учёта уже выбранных;
- **Δ к ручным** — разность NDCG@10 с ручным набором на одних и тех же пользователях; если интервал не содержит ноль, разница значима.

| Подход | Признаков | NDCG@10, 16.08 | Δ к ручным, 16.08 [95% ДИ] | Δ к ручным, 26.07 [95% ДИ] |
|---|---|---|---|---|
| Популярность | 1 | 0.1366 | −0.0158 [−0.0187, −0.0129] | −0.0207 [−0.0237, −0.0179] |
| Только базовые признаки | 12 | 0.1446 | −0.0078 [−0.0096, −0.0060] | −0.0090 [−0.0108, −0.0070] |
| **Ручные** | 12 + 29 | **0.1524** | — | — |
| Сетка + фильтр | 12 + 30 | 0.1525 | +0.0001 [−0.0016, +0.0019] | −0.0044 [−0.0060, −0.0026] |
| Жадный, случайный пул | 12 + 6 | 0.1536 | +0.0012 [−0.0003, +0.0028] | −0.0016 [−0.0033, +0.0001] |
| Жадный, пул от LLM | 12 + 6 | 0.1500 | −0.0024 [−0.0040, −0.0008] | −0.0031 [−0.0049, −0.0013] |
| Ручные + жадный (LLM) | 12 + 35 | 0.1544 | +0.0020 [+0.0009, +0.0031] | −0.0004 [−0.0016, +0.0008] |

LogLoss бинарной постановки на неделе 16.08: константа — 0.0417, базовые — 0.0370, ручные — 0.0364, жадный поиск — 0.0360, ручные + жадный — 0.0357.

Вычислительные затраты на ноутбуке с i3-1215U без GPU: сетка — 4 минуты, жадный поиск — около 40 минут, LLM-поиск — 45 минут, из них 24 минуты ожидания ответов бесплатной модели.

## Выводы

1. **Автоматический поиск достигает уровня ручного набора, но не превосходит его.** Жадный отбор нашёл 6 признаков, которые на обеих тестовых неделях не отличаются от 29 ручных значимо (+0.0012 и −0.0016).
2. **Прирост от объединения не воспроизвёлся.** Ручные + найденные признаки дали +0.0020 на неделе 16.08 и −0.0004 (в пределах шума) на неделе 26.07. Разница 0.002 NDCG между наборами сопоставима с изменчивостью между неделями, поэтому одной тестовой недели мало, чтобы утверждать превосходство.
3. **Работает отбор с учётом текущего набора.** Одномерный фильтр поверх сетки набирает варианты популярности, которые дублируют друг друга, и на второй неделе значимо проигрывает ручному набору.
4. **Поиск выбирает значения, которые человек обычно не перебирает:** затухание с полупериодом 7 и 14 дней, окно 60 дней.
5. **LLM как генератор кандидатов проиграла случайному на обеих неделях.** Формат грамматики модель соблюдает (89% допустимых спецификаций), но предложения узкие: 42% кандидатов используют масштаб 14 дней, 15% — бесполезные для ранжирования признаки пользователя, а на части шагов модель вернула неполный список.
6. **Ограничения:** сэмпл 100 тыс. пользователей, отбор по валидации частично подстраивается под её недели, в данных нет показов и повторных просмотров. Подробнее в разделе 7 ноутбука.

Отдельно описан баг, найденный по ходу работы: прореживание негативов через `shuffle(seed).over('user_id')` применяет одну перестановку ко всем пользователям. Модель от этого была хуже простой популярности (раздел 3.1 ноутбука).

## Как воспроизвести

Нужен Python 3.12 (на 3.14 могут не оказаться сборок части библиотек).

```bash
python -m venv .venv
.venv/Scripts/activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```

Данные. В репозитории KION архив `interactions.csv.zip` обрезан до 50 МиБ; полная версия лежит внутри `data_original.zip`:

```bash
mkdir data
# скачать https://github.com/irsafilo/KION_DATASET/archive/refs/heads/main.zip
unzip main.zip
unzip -j KION_DATASET-main/data_original.zip "data_original/*.csv" -d data/
```

В `data/` должны лежать `interactions.csv` (5 476 251 строка), `users.csv` и `items.csv`. Ноутбук проверяет число строк.

Запуск: открыть `solution.ipynb` и выполнить все ячейки. В `cache/` закоммичены результаты поисков (`search_*.json`) и все ответы LLM (`llm_log.jsonl`), поэтому полный прогон занимает около 15 минут и не требует ключа API. Чтобы повторить поиск с нуля, удалите `cache/search_*.json`. Для LLM-поиска нужен ключ OpenRouter в `.env` (см. `.env.example`).

Ограничение памяти: ноутбук рассчитан примерно на 4 ГБ свободной RAM. DuckDB ограничен 700 МБ и выгружает остальное на диск.

### На Kaggle

1. **Create → New Notebook**, затем **File → Import Notebook → вкладка GitHub**, вставить ссылку на `solution.ipynb` из этого репозитория.
2. В правой панели **Settings → Internet: On** (нужен подтверждённый телефон в аккаунте Kaggle).
3. **Run All.** Первая ячейка сама поставит библиотеки, склонирует репозиторий с кэшем и скачает полный архив KION. Если подключить свой датасет с `interactions.csv`, он будет использован вместо скачивания.

Ключ API на Kaggle не нужен: результаты поисков берутся из кэша. Для повторного LLM-поиска добавьте ключ в **Add-ons → Secrets** под именем `OPENROUTER_API_KEY`.

Все цифры в отчёте получены прогоном ноутбука на Kaggle. При локальном запуске на другом процессоре LightGBM обучается немного иначе, и метрики могут отличаться в третьем знаке; разброс по seed показан в разделе 6.6 ноутбука. Наборы признаков одинаковы, они берутся из `cache/search_*.json`.

```

requirements.txt    версии библиотек

cache/

  llm_log.jsonl     все запросы к LLM и ответы
  llm_stats.json    число запросов, токены, доля допустимых ответов

```
