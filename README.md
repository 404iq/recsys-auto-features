# Автоматическая генерация признаков для ранжирования рекомендаций

Исследование на датасете [KION](https://github.com/irsafilo/KION_DATASET) (МТС): может ли автоматический поиск по пространству признаков заменить ручной feature engineering для LightGBM-ранкера без потери качества.

Всё исследование в одном ноутбуке: [solution.ipynb](solution.ipynb). Здесь краткое изложение.

## Постановка

- **Задача:** по истории до даты `T` выбрать 10 тайтлов, которые пользователь посмотрит в неделю `[T, T+7)`. Уже просмотренное не рекомендуется.
- **Данные:** случайные 100 тыс. пользователей с полной историей, 573 тыс. просмотров.
- **Разбиение по неделям:** `train` 02–08.08, `val` 09–15.08, `test` 16–22.08.2021. Признаки каждой недели считаются только по событиям до её начала.
- **Двухстадийная схема:** популярность + ItemKNN дают около 170 кандидатов на пользователя (покрывают 44% позитивов), LightGBM `lambdarank` их ранжирует.
- **Метрики:** NDCG@10, Recall@10, MAP@10, ROC-AUC. Доверительные интервалы считаются бутстрепом по пользователям, сравнение с ручным набором — парным бутстрепом.

## Подход

Признаки описываются грамматикой: `(связь, тип события, окно или затухание, агрегация, нормировка, свёртка)`. Например, `ua:genre / complete / h30 / cnt / lift / max` означает «насколько чаще среднего пользователь досматривает жанры кандидата, с затуханием 30 дней». Спецификация компилируется в SQL для DuckDB. Пространство содержит 7 389 допустимых признаков, ручной набор — 29 его точек.

Утечки исключены конструктивно: единственный источник событий для признаков — таблица с отсечкой по дате. Это проверяется тестом: признаки не меняются, если удалить из лога все будущие события.

Сравниваются:

| Подход | Что делает человек | Как выбираются признаки |
|---|---|---|
| Ручные | придумывает 29 признаков | никак |
| Сетка + фильтр (как DFS) | задаёт сетку из 1 004 признаков | одномерный AUC внутри пользователя, удаление дублей |
| Жадный, случайный пул | задаёт пространство | 12 шагов: 24 кандидата → дешёвая оценка → 4 лучших → полная модель → принять, если NDCG растёт |
| Жадный, пул от LLM | задаёт пространство | то же, но кандидатов предлагает LLM (Nemotron 3 Ultra через OpenRouter), видя историю поиска |

## Результаты (тестовая неделя)

| Подход | Признаков | NDCG@10 | Recall@10 | Δ NDCG к ручным [95% ДИ] |
|---|---|---|---|---|
| Популярность | 1 | 0.1366 | 0.2156 | −0.0158 [−0.0187, −0.0129] |
| Только базовые признаки | 12 | 0.1446 | 0.2207 | −0.0078 [−0.0096, −0.0060] |
| **Ручные** | 12 + 29 | **0.1524** | 0.2268 | — |
| Сетка + фильтр | 12 + 30 | 0.1525 | 0.2256 | +0.0001 [−0.0016, +0.0019] |
| Жадный, случайный пул | 12 + 6 | 0.1536 | 0.2291 | +0.0012 [−0.0003, +0.0028] |
| Жадный, пул от LLM | 12 + 6 | 0.1500 | 0.2234 | −0.0024 [−0.0040, −0.0008] |
| Ручные + жадный (LLM) | 12 + 35 | **0.1544** | 0.2309 | **+0.0020 [+0.0009, +0.0031]** |

Вычислительные затраты на ноутбуке с i3-1215U без GPU: сетка — 4 минуты, жадный поиск — около 40 минут, LLM-поиск — 45 минут, из них 24 минуты ожидания ответов бесплатной модели.

## Выводы

1. **Автоматический поиск достигает уровня ручного набора.** Жадный отбор нашёл 6 признаков, которые не хуже 29 ручных (разница в пределах шума), а вместе с ручными дают значимый прирост +1.3%.
2. **Работает отбор с учётом текущего набора.** Одномерный фильтр поверх сетки набирает варианты популярности, которые дублируют друг друга.
3. **Поиск выбирает значения, которые человек обычно не перебирает:** затухание с полупериодом 7 и 14 дней, окно 60 дней. Из найденных значений в ручном наборе есть только окна 7 и 30 дней.
4. **LLM как генератор кандидатов проиграла случайному.** Формат грамматики модель соблюдает (89% допустимых спецификаций), но предложения узкие: 42% кандидатов используют масштаб 14 дней, 15% — бесполезные для ранжирования признаки пользователя, а на части шагов модель вернула неполный список.
5. **Ограничения:** одна тестовая неделя, разности между подходами сопоставимы с шумом, отбор по валидации частично переобучается, в данных нет показов и повторных просмотров. Подробнее в разделе 7 ноутбука.

Отдельно описан баг, найденный по ходу работы: прореживание негативов через `shuffle(seed).over('user_id')` применяет одну перестановку ко всем пользователям. Модель от этого была хуже простой популярности (раздел 3.1 ноутбука).

## Как воспроизвести

Нужен Python 3.12 (на 3.14 могут не оказаться сборок части библиотек).

```bash
python -m venv .venv
.venv/Scripts/activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```

Данные. В репозитории KION архив `interactions.csv.zip` обрезан до 50 МиБ; полная версия лежит внутри `data_original.zip`:

```bash
mkdir data
# скачать https://github.com/irsafilo/KION_DATASET/archive/refs/heads/main.zip
unzip main.zip
unzip -j KION_DATASET-main/data_original.zip "data_original/*.csv" -d data/
```

В `data/` должны лежать `interactions.csv` (5 476 251 строка), `users.csv` и `items.csv`. Ноутбук проверяет число строк.

Запуск: открыть `solution.ipynb` и выполнить все ячейки. В `cache/` закоммичены результаты поисков (`search_*.json`) и все ответы LLM (`llm_log.jsonl`), поэтому полный прогон занимает около 15 минут и не требует ключа API. Чтобы повторить поиск с нуля, удалите `cache/search_*.json`. Для LLM-поиска нужен ключ OpenRouter в `.env` (см. `.env.example`).

Ограничение памяти: ноутбук рассчитан примерно на 4 ГБ свободной RAM. DuckDB ограничен 700 МБ и выгружает остальное на диск.

## Структура

```
solution.ipynb      исследование целиком
requirements.txt    версии библиотек
.env.example        шаблон для ключа OpenRouter
cache/
  search_*.json     принятые признаки и история каждого поиска
  llm_log.jsonl     все запросы к LLM и ответы
  llm_stats.json    число запросов, токены, доля допустимых ответов
  timings.json      время шагов при первом прогоне без кэша
```
